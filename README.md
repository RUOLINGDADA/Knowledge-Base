# 通用个人知识库

面向任何主题的个人知识库模板，以 Obsidian 为主要使用方式。

这套方法既适合记录技术开发，也适合整理学习、工作、研究、读书、项目、生活决策和日常资料。它不追求收集大量内容，而是把一次提问、一次实践、一次会议或一段资料沉淀成下一次可以复用的知识。

> 核心方法：**事实与目标 → 关键过程 → 可复用结论 → 限制与验证 → 关联知识**

## 快速开始

### 方式一：使用 Obsidian（推荐）

1. 将本仓库克隆到本地，或直接下载 ZIP。
2. 在 Obsidian 中选择“打开其他仓库”，打开 `Knowledge-Base` 根目录作为 Vault。
3. 使用 Vault 已配置的临时目录 `待整理的新笔记/` 保存刚创建的笔记，确认内容后移动到合适的多级分类目录。
4. 将代码完整实现保存在项目仓库，知识库只保留关键片段、参数和踩坑信息。
5. `.obsidian/` 保存当前 Vault 的配置；除非有意共享设置，不要随意删除或覆盖它。
6. 通过 Git 提交笔记、附件和必要的 Vault 配置，保留每次修改记录。

```bash
git clone https://github.com/<your-name>/<your-repository>.git
cd <your-repository>
```

### 方式二：配合 AI 使用

1. 将本文的[AI 知识库助手提示词](#ai-知识库助手提示词)复制到 AI 工具的系统提示词栏，或让 AI 读取根目录 `agent.md`。
2. 用自然语言描述调试过程、学习内容或代码功能。
3. 检查助手生成的 Properties、分类、层级、标签、双链和技术细节。
4. 将确认后的 Markdown 笔记保存到 `待整理的新笔记/`，再用 Obsidian 移动到合适的多级分类目录。

## Obsidian 设置

本仓库根目录就是 Obsidian Vault。仓库已包含 `.obsidian/` 配置目录、`附件/` 附件目录和 `待整理的新笔记/` 临时笔记目录。

### 推荐设置

- **附件默认位置**：设置 → 文件与链接 → 新附件的默认位置 → `附件` 文件夹。
- **新建笔记位置**：设置 → 文件与链接 → 新建笔记的默认位置 → `待整理的新笔记` 文件夹。
- **链接格式**：优先使用 Wikilink（例如 `[[串口通信_波特率不一致导致乱码]]`），便于重命名和反向链接。
- **使用 Wiki 链接**：保持开启；需要兼容 GitHub 等普通 Markdown 渲染器时，再使用相对路径链接。
- **文件删除**：建议设置为移动到系统回收站，避免误删工程记录。

### Obsidian 笔记属性

每篇正式笔记必须在顶部使用 YAML Properties，标签同时保留在 `tags` 属性中：

```yaml
---
分类: 技术/版本控制
层级: 精通层
类型: 问题排查型
主题:
  - Git
技术栈:
  - git
  - github
tags:
  - Git
  - 版本控制
状态: 已验证
创建日期: YYYY-MM-DD
---
```

属性值必须与正文中的分类、层级和标签一致。日期使用 `YYYY-MM-DD`，未知信息写 `待验证`，不要猜测。

### 双链与附件

- 相关笔记使用 `[[笔记名]]` 建立双向知识链接，必要时使用显示文本：`[[STM32_定时器输出PWM|PWM 输出]]`。
- 链接到章节使用 `[[笔记名#章节标题]]`，链接到块使用 Obsidian 的块 ID。
- 图片、波形、数据手册等文件放入 `附件/` 或其子目录，并在笔记中使用 `![[附件/文件名.png]]` 嵌入。
- 不要把附件散落在分类目录中；文件名使用主题和日期或版本，避免 `image1.png` 这类无意义名称。
- 重命名笔记应使用 Obsidian 的重命名功能，保持双链自动更新。

## 目录与多级结构

目录层级没有固定深度，可以按主题、项目、时间、来源或内容类型建立任意多级子目录。目标是易找、少重复、同类集中、长期可维护，不为了凑层级而拆分，也不把所有笔记平铺在一个目录中。

```text
Knowledge-Base/
├── 首页.md             # Obsidian Vault 导航入口
├── README.md
├── agent.md           # AI 输出规范
├── .obsidian/         # Obsidian Vault 配置
├── 资料速查/
│   └── Git/
│       ├── Git_专题索引.md
│       ├── 命令/
│       │   └── Git_常用命令与场景.md
│       ├── 配置/
│       │   └── Git_提交身份配置.md
│       └── 远程同步/
│           └── Git_提交后未同步到GitHub.md
│   └── Windows/
│       ├── OpenSSH/
│       │   ├── Windows_OpenSSH_专题索引.md
│       │   └── ...
│       └── 树莓派网络共享/
│           ├── Windows_树莓派网络共享_专题索引.md
│           └── ...
├── 待整理的新笔记/     # Obsidian 新建笔记暂存区
└── 附件/               # 图片、波形、PDF 等附件
```

这是当前实际结构的主要示例。后续可新增“学习”“工作”“项目”“生活”等顶层分类，并继续按项目、技术栈、年份或专题细分。目录结构与笔记中的知识层级无关。

一个专题包含多篇笔记时，在专题根目录建立索引笔记，例如 `Git_专题索引.md`；根目录 `首页.md` 负责汇总一级入口。

### 文件命名建议

使用“主题 + 场景”的方式命名，避免只使用日期或模糊名称。Obsidian 会自动维护双链，重命名应在 Obsidian 中完成。

```text
串口通信_波特率不一致导致乱码.md
ROS2_节点与话题.md
STM32_定时器输出PWM.md
树莓派_串口权限配置.md
```

推荐使用稳定、唯一、便于双链搜索的文件名；同一主题不要同时创建多个近似名称。

## 三层知识分级

| 层级 | 判断标准 | 记录重点 | 复习目标 |
| --- | --- | --- | --- |
| **精通层** | 能独立实现、调试并解释原因 | 完整排查链路、关键参数、可复现方案 | 遮住答案后复现解决过程 |
| **理解层** | 能说明工作流程，但还不能稳定落地 | 核心逻辑、接口关系、常见误区 | 用自己的话讲清楚原理 |
| **了解层** | 知道用途和查找方向，尚未深入实践 | 一句话定义、关键词、可靠资料入口 | 知道何时使用、去哪里查 |

层级不是永久标签。完成一次真实项目验证后，可以把笔记从“了解层”升级为“理解层”或“精通层”。

这里的“三层”只表示知识掌握程度，与文件夹有几级无关；目录可以是一层，也可以按需要继续细分为任意多级。

## 笔记类型

### 1. 问题排查型

适合记录技术故障、流程异常、工作问题、判断失误及其定位过程。

```markdown
---
分类: 技术/版本控制
层级: 精通层
类型: 问题排查型
主题: [Git]
技术栈: [git, github]
tags: [git, 版本控制, 精通层]
状态: 已验证
创建日期: YYYY-MM-DD
---

# [分类] 问题主题

> **分类**：根据主题填写的稳定分类
> **层级**：精通层 / 理解层 / 了解层
> **标签**：#技术栈 #模块 #关键词 #层级

## 问题现象

描述触发条件、实际表现和预期结果之间的差异。

## 排查过程

1. 检查了什么，以及观察到什么现象。
2. 根据现象缩小到哪个模块。
3. 最终确认的直接原因。

## 最终解决方案

- 写出可以重新执行的解决步骤。
- 记录需要保持一致的配置、接线或版本。

## 核心代码 / 配置片段

只保留最关键的 3～5 行，并标注修改点。

## 踩坑记录

- 为什么会出现这个问题，新手容易忽略什么。
- 同类问题如何快速判断。

## 原理 / 因果点睛

用 1～2 句话说明为什么会产生这个现象，并联系实际证据或验证方式。
```

### 2. 知识学习型

适合记录概念、课程、书籍、方法、协议、理论或新领域知识。

```markdown
---
分类: 学习/知识方法
层级: 理解层
类型: 知识学习型
主题: [知识点]
tags: [知识点, 核心概念, 理解层]
状态: 待验证
创建日期: YYYY-MM-DD
---

# [分类] 知识主题

> **分类**：根据主题填写的稳定分类
> **层级**：理解层
> **标签**：#技术栈 #知识点 #核心概念 #理解层

## 核心定义

用自己的话说明它是什么、解决什么工程问题。

## 核心逻辑 / 工作流程

1. 输入是什么。
2. 系统按什么顺序处理。
3. 输出是什么，哪些模块会使用输出。

## 关键参数 / 指标

| 参数 | 影响 |
| --- | --- |
| 参数一 | 参数改变后会出现什么实际现象 |
| 参数二 | 如何选择或验证 |

## 常见误区

记录容易混淆的概念、边界条件和使用限制。

## 原理 / 因果点睛

用 1～2 句话讲清本质，并联系实际工程现象。
```

### 3. 代码功能型

适合记录已经实现的程序、自动化、配置、工具、工作流或功能模块。

```markdown
---
分类: 技术/自动化
层级: 精通层
类型: 代码功能型
主题: [功能模块]
技术栈: [python]
tags: [功能模块, 精通层]
状态: 已验证
创建日期: YYYY-MM-DD
---

# [分类] 功能主题

> **分类**：根据主题填写的稳定分类
> **层级**：精通层 / 理解层
> **标签**：#编程语言 #功能模块 #层级

## 功能描述

说明功能、输入、输出和使用场景。

## 核心逻辑

1. 接收或读取输入。
2. 校验、转换并处理数据。
3. 调用硬件或系统接口。
4. 返回结果并处理异常。

## 关键代码片段

只保留最能体现核心逻辑的 3～5 行代码，并写必要注释。

## 踩坑记录

- 编写或调试时遇到的问题。
- 环境依赖、权限、版本兼容和边界条件。

## 原理 / 因果点睛

说明代码如何与操作系统、驱动、总线或硬件交互。
```

### 4. 项目复盘型

适合记录项目、活动、实验、学习计划或阶段性工作的结果与经验。

建议结构：`目标与范围 → 最终结果 → 关键决策 → 问题与原因 → 可复用经验 → 后续行动`。

### 5. 资料速查型

适合记录命令、参数、术语、接口、清单、操作步骤和可靠资料入口。

建议结构：`用途 → 语法或参数 → 最小示例 → 限制与版本 → 来源 → 相关笔记`。

同一专题有多篇资料时应集中到子目录，例如：

```text
资料速查/
└── Git/
    ├── 常用命令.md
    ├── 提交身份配置.md
    ├── 远程同步.md
    └── 冲突排查.md
```

### 6. 通用知识型

适合保存无法归入以上类型、但值得长期检索的内容，如人物、地点、观点、生活经验、写作素材或决策依据。

建议结构：`一句话结论 → 关键事实 → 适用边界 → 示例或证据 → 相关笔记`。

## 标签规范

标签用于跨目录检索，命名应稳定、简短、可复用。

- 技术栈或工具标签尽量使用小写：`#python`、`#ros`、`#excel`、`#linux`；非技术主题使用自然、稳定的主题标签。
- 分类和主题标签保持统一，例如 `#项目管理`、`#读书笔记`、`#数据库`、`#串口通信`。
- 层级固定为：`#精通层`、`#理解层`、`#了解层`。
- 同一概念只保留一个主要写法，例如统一使用 `#串口通信`，不要交替使用 `#串口`、`#串口通讯`。
- 一篇笔记建议保留 3～6 个标签，避免标签泛滥。

示例：

```text
#stm32 #串口通信 #乱码排查 #精通层
#ros2 #节点 #话题通信 #理解层
#python #键盘控制 #小车 #精通层
```

## 记录工作流

1. **先记目标与事实**：记录问题、目的、来源、时间、输入和预期结果。临时内容先放入 `待整理的新笔记/` 或 `00_每日笔记/`。
2. **再记关键过程**：保留真正产生判断、进展或结论的步骤，不堆砌无效尝试。
3. **明确可复用结论**：写清操作步骤、决策依据、参数、示例、适用条件和验证方式。
4. **补充限制与踩坑**：把容易再次发生的错误、反例、依赖和边界单独写出来。
5. **建立关联**：用 `[[相关笔记]]`、章节链接和附件嵌入连接上下文，避免复制同一份内容。
6. **归档与复盘**：根据主题移动到合适的多级目录；目录可以随知识增长继续细分或合并。
7. **升级层级**：经过实践、复核或独立复现后，再调整知识层级和状态。

## AI 知识库助手提示词

将下面内容粘贴到 AI 工具的系统提示词栏，或让 AI 读取根目录 `agent.md`，即可按本知识库规范整理输入内容并直接归档到 Obsidian。

```text
你是通用知识库与问题解决助手，服务于任何主题。先判断用户是在提问、执行任务，还是要求整理/归档笔记；普通问题直接回答，不强行套用笔记模板。需要归档时，输出以 Obsidian 为目标的 Markdown 笔记。

要求：
1. 笔记类型可选：问题排查型、知识学习型、代码/功能型、项目复盘型、资料速查型、通用知识型。
2. 需要归档时自动判断层级：精通层、理解层或了解层；不要夸大掌握程度。
3. 分类由用户已有目录优先决定，否则根据主题生成稳定分类；不限制领域，也不强行使用示例领域。
4. 技术栈或工具标签尽量小写，主题标签稳定简短，层级标签固定为 #精通层、#理解层、#了解层。
5. 结论必须联系实际场景、证据、输入输出、限制或验证方法；非技术主题也要说明因果和适用边界。
6. 经验型笔记必须记录踩坑、反例、依赖、版本、权限、边界或风险；没有信息时写“待验证”。
7. 代码、命令或配置只保留最核心的 3～5 行，完整内容使用文件链接或附件引用。
8. 正式笔记顶部必须包含 YAML Properties：分类、层级、类型、主题、tags、状态、创建日期；技术内容可额外添加技术栈。
9. 使用 Obsidian 双链 `[[笔记名]]`、章节链接和 `![[附件/文件名]]`；不得虚构不存在的文件或链接。
10. 目录层级不限，按主题自然组织；同类内容应集中到子文件夹，例如 `资料速查/Git/`，不要将相关笔记全部平铺。
11. 不写客套话、无关拓展、重复总结或结尾提问，笔记完成后直接结束。

问题排查型建议包含：
问题现象、排查过程、最终解决方案、关键代码/数据/配置、踩坑记录、原理点睛。

知识学习型必须包含：
核心定义、核心逻辑/工作流程、关键参数/指标、常见误区、原理/因果点睛。

代码/功能型建议包含：
功能描述、核心逻辑、关键代码片段、踩坑记录、原理点睛。

当用户信息不足时，基于已知内容整理，不虚构测试结果；无法确定的内容明确标记为“待验证”。
```

## 示例输入

### 串口乱码排查

```text
今天用 pyserial 写树莓派和 STM32 的串口通信，发送的数据全是乱码。后来发现树莓派波特率是 9600，STM32 是 115200，改成一致后恢复正常。最开始运行还提示没有权限，确认是用户不在 dialout 组，加入用户组后解决。
```

适合归档到 `技术/嵌入式/串口通信/问题排查/`，标签可使用：

```text
#python #stm32 #linux #串口通信 #精通层
```

```text
今天学习主动回忆：看完材料后先合上资料，用自己的话回答问题，再对照原文找遗漏。它比反复阅读更容易暴露“看懂了但说不出来”的知识缺口，目前还没有连续实践验证。
```

适合归档到 `学习/学习方法/记忆方法/`，标签可使用：

```text
#学习方法 #主动回忆 #记忆 #了解层
```


## 其他笔记软件兼容方案

Obsidian 是本仓库的主格式和事实来源。迁移到其他软件时，先保留原始 Markdown 备份，再按目标软件能力做降级转换；不要为了兼容而破坏 Obsidian 原文件。

### 通用 Markdown / GitHub / VS Code

- YAML Properties 通常可作为普通文本保留；不支持 Properties 面板的软件可将其转换为正文表格。
- 将 `[[笔记名]]` 改为相对路径链接，例如 `[笔记名](../主题/笔记名.md)`。
- 将 `![[附件/文件.png]]` 改为 `![说明](../附件/文件.png)`。
- 保留标题、列表、表格、代码块和引用，避免依赖 Dataview、Canvas 或插件语法。

### Notion

1. 使用 Notion 的 Markdown 导入功能导入笔记和附件。
2. 将 YAML Properties 的 `分类`、`层级`、`类型`、`主题`、`状态`、`创建日期` 映射为 Notion 数据库属性；`tags` 映射为多选属性。
3. Wikilink 不会始终自动转换，导入后检查并改为 Notion 页面链接或普通 Markdown 链接。
4. 多级文件夹改为“顶层页面 → 子页面”或数据库的分类属性；保留原文件名作为页面标题。

### Logseq

- Logseq 支持 Markdown 和 `[[双链]]`，通常可以直接导入；将 YAML 保留在文件顶部并检查属性识别结果。
- 需要大纲化时，将一级标题转换为页面或块，避免把长段落全部压成同一级块。
- `![[附件/...]]` 可直接保留或改为 Markdown 图片链接，迁移后检查附件相对路径。

### Joplin

- 使用 Markdown 导入，YAML 不支持为原生字段时可保留为正文，或转换为开头的属性表格。
- 将 Wikilink 转为相对 Markdown 链接或 Joplin 笔记链接；图片和附件导入后逐一检查。
- 多级目录映射为 Joplin 笔记本和子笔记本，目录深度按检索便利性调整。

### 语雀及其他在线 Markdown 编辑器

- 粘贴或导入 Markdown 前，建议移除 YAML 分隔线，并将 Properties 转成“元信息”表格放在正文开头。
- 将双链改成平台支持的文档链接；将附件嵌入改成平台上传后的图片或文件链接。
- 不依赖 Obsidian 专属语法（Callout、块 ID、Dataview 查询）；保留标题、表格、代码块和普通链接。

### 迁移检查清单

- 标题、代码块、表格、列表和中文文件名显示正常。
- Properties 中的分类、层级、标签、状态和日期没有丢失。
- 双链、章节链接、图片、PDF 和其他附件都能打开。
- 多级目录仍保持同类集中，没有因为导入而全部平铺。
- 迁移后的修改需要回写 Obsidian 主库，避免出现两个互不一致的版本。
